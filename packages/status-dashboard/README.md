# Dome Keeper status dashboard

A small Vue 3, TypeScript, and Vite dashboard using `@proj-airi/ui` and UnoCSS.

```sh
bun run --cwd packages/status-dashboard dev
```

## Live

Live mode polls `GET /api/status` once per second. The Vite development plugin reads `airi-dome-keeper-status.json` from the operating system's temporary directory, so no second frontend process is needed.

An unavailable producer snapshot is `{ "available": false, "run_time_seconds": 0 }`; status cards render only for an available run.

## Replay

Start a recorded run with `mise run godot:record`; pass `-- --fps 60` to override the default 30 FPS. The mise task writes each session under `recordings/session_<UTC timestamp>_<UUID>/` in the repository root.

Replay mode consumes full-snapshot events and synchronizes them to the manually selected MP4 with `movie_frame / fixed_fps`. It supports play/pause, previous and next event, movie scrubbing, playback speed, and transition reasons.

Replay is manual-only: select a replay JSON, then its MP4. The Vite bridge serves only the Live status file and never discovers or serves recorded sessions.

```sh
bun run --cwd packages/status-dashboard typecheck
bun run --cwd packages/status-dashboard build
```

## Status Dashboard

The following is the current binding observer and replay contract.

- Use the small Vue 3, TypeScript, and Vite package at `packages/status-dashboard/` to display and replay local Dome Keeper runs. Poll `GET /api/status` once per second in `Live` mode with no overlapping requests and keep the last valid snapshot visible when transport fails. The inline Vite `configureServer` plugin bridges only the live status file; replay files are selected manually and must not be discovered or served by Vite. Do not add demo/sample state, an HTTP server to the Godot mod, or a separate Node backend.
- Have the persistent rule teacher write its current live snapshot once per second to `airi-dome-keeper-status.json` in the operating system's temporary directory, resolving the same standard temporary-directory environment variables used by Node's `os.tmpdir()`. The existing Vite development process reads that file for `/api/status`; this live transport is separate from event-driven replay recording.
- Use `@proj-airi/ui` with UnoCSS and its reset/style entrypoints so the observer shares AIRI's light, rounded, low-contrast visual language instead of introducing a separate game-HUD aesthetic. Use UnoCSS utilities and shortcuts for layout-specific status surfaces, keep raw CSS limited to document-level baseline rules, and use the library for shared primitives such as progress, callout, and button.
- Group each supported upgradeable runtime value with the level of its explicit bought-upgrade chain, using level zero for the base equipment and the numbered upgrade suffix after purchase. Keeper runtime information includes base and current effective movement speed with the `jetpackSpeed1..4` level, configured carry loss and current load slowdown with the `jetpackStrength1..4` level, drill strength with the `drill1..4` named level, and carried inventory. Dome runtime information includes current and maximum health with the `dome1health1..2` level, stored inventory, effective Laser attack strength with the `laserStrength1..4` level, both normal and firing maximum Laser movement speed with the shared `laserMove1..3` level, and the current normal-Laser aim observation. Aim observation identifies the selected monster by runtime UID, wave counter, and kind; reports its current damageability, signed angular error in radians, and the first collider plus ray order. Treat repeat purchases of `drill4` as changes to the runtime value while its named upgrade level remains four. Derive levels from explicit bought upgrade IDs, never from numeric values or visual variants, because modifiers and other upgrades may change the same runtime values. Do not duplicate Laser attack strength under Keeper data or expose raw Laser modifier fields alongside their effective products. Do not add teacher/controller labels, return-duration data, position/station fields, active-purchase state, or other fields outside the confirmed observer contract. Keep the `Upgrades` surface focused on pending intents plus the resolved next target and its current resource cost.
- Show the one-based current or upcoming wave number from the authoritative team `monsters.cycle + 1`, the wave time remaining, and active monsters grouped by runtime kind with the corresponding count and health data. Listen to the runtime cycle property so replay snapshots advance immediately after a settled wave; do not infer the number from recorded events. Do not add a separate battle-active or battle-settled callout because zero countdown plus a positive living count already communicates the active-wave condition.
- Keep the current-state summary data-led: do not add a decorative `DK` monogram tile or another invented avatar without game-state meaning.
- Keep exactly two dashboard modes. `Live` reads the current status snapshot. `Replay` requires the user to select both a replay JSON and its MP4, uses that movie as its only gameplay imagery, directly selects stored full snapshots, and provides play/pause, previous/next event, scrub/seek, and playback-speed controls while showing transition reasons. Replay must not discover a latest session, reconstruct state from patches, or display event screenshots.
- Create recorded sessions through one repository command that writes each session under `recordings/session_<filesystem-safe UTC ISO timestamp>_<UUID>/` in the repository root, then starts the target Godot project with Movie Maker enabled via `--write-movie` and an explicitly declared `--fixed-fps`. The timestamp makes folders human-readable and chronologically sortable, while the UUID preserves collision resistance; it is folder metadata only and must not participate in replay synchronization. Persist only the fixed FPS needed by replay synchronization; the user pairs the resulting JSON and MP4 by selecting both files. Do not depend on editor Movie Maker state, wall-clock speed, an external recorder, visual markers, or manual calibration. Movie Maker starts automatically after the splash screen and writes every rendered frame with fixed non-real-time simulation. If its built-in AVI output needs conversion for browser playback, automate that conversion while preserving the frame timeline. Shut the process down normally so the movie writer can finalize its output.
- Make replay recording event-driven rather than periodic. At session start and on accepted `Data.listen` changes, resource pickup, monster spawn/death, confirmed upgrades, normal-Laser target, damageability, or first-collider changes, acquired-target firing-start observations, teacher state transitions, and terminal teacher failures, append an event containing a complete observer snapshot before teardown clears the recording state; never store RFC 6902 patches, viewport screenshots, PNG data, Base64 data, or duplicated video frames. Capture each event's Movie Maker frame and snapshot immediately, but batch the growing replay JSON to disk once per second and flush it before normal teardown so target-switch telemetry cannot synchronously rewrite the whole file ahead of weapon input on every physics tick. Laser target-change reasons distinguish initial minimum-turn selection, target death or departure, visibility loss, damageability-tier replacement, and eligible first-collider takeover when observable. Top-level teacher-state and `EXPLORE` sub-state transitions must include their previous value, next value, and concrete trigger reason. Other tracked changes retain the complete current player, stat, dome, monster, and upgrade state needed to explain the run.
- Use `Engine.get_process_frames()` as the authoritative Movie Maker frame clock. Record its movie-frame value for every full snapshot and persist the session's fixed FPS. Seek with `movie_frame / fixed_fps`, and do not use `Engine.get_frames_drawn()` because skipped draws can diverge from MovieWriter output. Keep `run_time_seconds` only as displayed unpaused game time. Do not synchronize by wall-clock timestamps, `Time.get_ticks_msec()`, event order, YOLO filenames, image recognition, or user input. Fail session startup if the movie/frame configuration is missing or inconsistent.
- The live and replay observer contract exposes only: the player's current top-level state and current `EXPLORE` sub-state when applicable; grouped Keeper movement, carry, and drill runtime values with their upgrade levels plus carried iron/cobalt/water; grouped Dome health and Laser attack/movement runtime values with their upgrade levels, the current selected monster and aim observation, plus stored iron/cobalt/water; the one-based current or upcoming wave number, wave time remaining, and active monsters grouped by runtime kind with count and health; pending upgrade intents; and the resolved next upgrade with its current nonzero resource cost. The aim object is optional only so the dashboard can display recordings created before aim telemetry was added. Do not duplicate derived ratios, raw modifier inputs, monster totals, run time inside an event, target-switch reasons already identified by the event header, or transition domains already identified by the event type. Because both JSON producers and consumers are owned by this repository, parse directly into the shared TypeScript contract instead of converting values to `unknown` and hand-writing pseudo-validation; treat JSON syntax and missing files as the actual boundary failures.
- Keep Movie Maker/replay recording parallel to the YOLO dataset collector. Do not change YOLO classes, object-tree labels, `640x640` gray letterboxing, pause-menu/TechTree exclusion, target balancing, or image-label pairing for replay. Movie Maker may contain frames that YOLO rejects, and replay movie frames are not YOLO `capture_index` values. Do not reuse movie frames as labeled YOLO images.
